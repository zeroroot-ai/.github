# Security Policy

This is the default security policy for every repository in the
[`zeroroot-ai`](https://github.com/zeroroot-ai) organisation. GitHub shows it on
the `Security` tab of any repository that does not carry its own `SECURITY.md`.
A repository MAY publish a more specific policy — `zeroroot-ai/setec` does,
because it makes microVM isolation claims that need their own threat model. When
a repository has its own file, that file wins for that repository. Everything
below still applies to the reporting channel, the timeline, and the safe-harbour
terms.

ZeroRoot builds offensive-security tooling. The platform holds tenant
credentials, runs untrusted code, and reaches customer-nominated targets, so a
defect here can affect people who are not us. Report it and we will act on it.

## Reporting a vulnerability

**Do not open a public issue, discussion, or pull request for a security
problem.** Use one of the private channels below.

1. **GitHub private vulnerability reporting — preferred.** Open the affected
   repository's `Security` tab and select **Report a vulnerability**. This is
   enabled on every public repository in the organisation. It creates a draft
   advisory visible only to the maintainers and to anyone you invite, and it is
   the fastest route to a maintainer.
2. **Email:** `security@zeroroot.ai`. Use this if the report spans more than one
   repository, if it concerns a repository that is not public, or if it concerns
   the hosted service rather than the source. If you need to encrypt the
   message, ask for a key in the first email and we will reply with a current
   fingerprint.

Please include what you have. A report is useful even when it is incomplete:

- What the issue is and why you consider it a security problem.
- Which component and version — repository, release tag, image digest, or the
  hosted environment.
- A minimal reproducer or proof of concept, if you have one.
- Any logs, manifests, or traces that help us confirm it.
- The name and contact you would like credited in the advisory, or a note that
  you prefer to stay anonymous.

## Response timeline

- **Acknowledgement:** within 72 hours we confirm receipt and assign a
  maintainer to triage.
- **Initial assessment:** within 10 business days we share our reading of the
  severity and a rough remediation plan.
- **Fix target:** Critical and High issues target a patched release within 30
  days of the initial assessment. Medium and Low issues are batched into the
  next regular release.
- **Public disclosure:** we coordinate the timing with you. The default window
  is 90 days from the original report, or sooner once a fix ships and is broadly
  available. We ask for an extension only when active exploitation or a deeply
  invasive fix makes one necessary, and we explain why.

We publish a GitHub Security Advisory for every confirmed vulnerability in
first-party code, with a CVE where one applies, and we credit reporters unless
they ask us not to.

## Scope

**In scope** — the source in this organisation, the container images we publish
to `ghcr.io/zeroroot-ai/*`, the Helm charts we publish, and the hosted ZeroRoot
Cloud service.

Findings we particularly want:

- Cross-tenant access of any kind — data, credentials, graph state, or mission
  results.
- Escape from a setec microVM, or any path that reaches the host or another
  guest from inside one.
- Authentication or authorisation bypass, including anything that gets a caller
  past the ext-authz chain or produces a capability grant it should not have.
- Disclosure of secrets — tenant KEKs, provider API keys, bootstrap tokens,
  SPIFFE material.
- Supply-chain defects in what we publish: an image, chart, or module that does
  not match the source it claims to be built from.

**Out of scope** — reports generated by a scanner with no demonstrated impact;
vulnerabilities in third-party dependencies that we ship but do not control,
unless you can show they are reachable in our configuration (tell us anyway, we
track those, but they are handled as dependency maintenance rather than as an
advisory); social engineering of our staff; physical attacks; volumetric denial
of service; and findings that require an already-compromised host or an already
privileged account.

Third-party CVEs in an image we publish are real work and we do track them, but
they are triaged as maintenance. Please still report one if you can show it is
reachable — reachability is the part we cannot always determine ourselves.

## Safe harbour

If you make a good-faith effort to follow this policy, we will not pursue or
support legal action against you for your research, and we will treat your
report as authorised access. Good faith means:

- Test only against your own accounts, tenants, and resources — never another
  customer's.
- Stop at proof. Do not exfiltrate data, pivot further than needed to show
  impact, degrade the service, or hold anything to ransom.
- Delete any data you did come across, and tell us what you saw so we can assess
  the exposure.
- Give us the disclosure window above before going public.

If a third party brings an action against you for research that followed this
policy, we will say publicly that it was authorised.

## Supported versions

Every repository in the organisation is pre-1.0 and releases from `main`.
Security fixes land on the most recent minor release line only; we do not
backport to older lines. Track the latest release of the component you run. When
a repository adopts a longer maintenance window, it will say so in its own
`SECURITY.md`.

## What we do on our own side

So you know what to expect from the code you are looking at:

- Secret scanning with push protection, Dependabot security updates, CodeQL, and
  container scanning run on every repository in the organisation.
- Private vulnerability reporting is enabled on every public repository.
- Every published image is built in CI from a pinned base and scanned before
  release; findings are tracked publicly as issues rather than suppressed.
